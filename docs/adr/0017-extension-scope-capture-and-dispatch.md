# 扩展收敛为工作台的浏览器端:只做收录与投递执行,不做独立同步

Status: accepted(2026-11-24 与用户逐项定案;本 ADR 推翻 ADR 0010 的「保留 Wechatsync 全部用户功能」「侧栏之外的入口」「功能边界」三行与 ADR 0009 的扩展范围;vendored fork、GPL 边界、Native Messaging 配对、收录与投递契约不变)

## 背景

起因是「任意网页都显示同步文章」。查明不是 bug:通用 FAB 受 `floatingButtonEnabled` 控制且默认关(已开着才会出现),但公众号文章页的专用 FAB 不受这个开关控制(`content/weixin.ts:18-28` 只要页面有 `#js_content` 就注入)。

真正的根因是身份没定:ADR 0010 把 Wechatsync 整仓 vendor 进来时,连它作为独立产品的功能面一起继承了——当前页同步、历史页、CMS 自建站、页面注入入口。这几条要么不落工作台数据,要么与工作台重复,要么接不进来:

- 当前页同步不产生灵感或作品,只在扩展自己的 `syncHistory` 里留痕;工作台不知道这次同步发生过。
- 历史页与 `Work.publication.dispatches` 重复。
- CMS 自建站目前也投不出去:CMS 账户 id 是动态的 `cms_<时间戳>`,不在静态 `BRIDGE_ADAPTERS` 里,`src/bridge.js:342` 会过滤掉,回执校验(`bridge.js:289`)也会丢弃。这是接线缺口,不是删掉自建站的理由。
- 侧栏 tab 写「收录」,GLOSSARY 与 ADR 0010 写「收进」,FAB 写「同步文章」:同一个动作三个词。

工作台对扩展的真实依赖只有四条:收录(网页 → inbox → 灵感)、投递执行(outbox → 适配器 → 草稿 → receipts → dispatches)、账号与自建站目标、配对。

## 决策

| 事项 | 决策 |
| --- | --- |
| 身份 | 扩展是工作台的浏览器端,不是可独立使用的同步产品。每个功能都必须服务工作台的数据闭环:网页进灵感,作品出草稿。 |
| 保留 | 收录(当前页/选区 → inbox);投递执行(只跑工作台下发的任务,显示逐平台进度与结果);账号(DSL 平台登录态与 CMS 自建站账户);设置与配对;适配器与预处理(含 WordPress / Typecho / MetaWeblog);头条 fetch 中继;提取内容脚本(`EXTRACT_SELECTION` / `EXTRACT_ARTICLE`)。 |
| 删除 | 当前页独立同步;历史页与 `syncHistory` 持久化;通用悬浮按钮与 `floatingButtonEnabled` 设置;公众号文章页 FAB 与同步 iframe;公众号后台编辑器 FAB 与 iframe。 |
| 侧栏 | 三个 tab:收录 / 投递 / 账号;默认收录;设置由齿轮进入。投递页只保留工作台下发的任务,不再有「当前页」来源。 |
| 投递菜单 | 工作台发布对话框列已登录的 DSL 平台,并单独一组「自建站」列已连接的 CMS 账户;未登录/未连接/用户在设置里隐藏的折叠到「更多」。适配器代码保留 20 个,不因菜单收缩而删。 |
| 投递目标快照 | 扩展经本地助手上报一份只读快照:DSL 平台 id 与是否已登录;CMS 账户的 id / 类型 / 名称 / 地址 / 用户名 / 是否已连接;设置里隐藏的平台 id。不含密码与 cookie。工作台据此渲染投递菜单并校验目标。 |
| 快照载体 | 助手原子写 `bridge/targets.json`;工作台新增只读路由 `bridge/targets`,发布对话框打开时读取;文件缺失时退回静态 DSL 表。 |
| 投递呈现 | 任务只推给已打开的侧栏并切到「投递」;不再为每次投递弹 396×560 窗口。进度在侧栏,结果在工作台的 `dispatches`。 |
| 自建站 id | CMS 账户 id 从 `cms_<时间戳>` 改为稳定 id(`type` + 规范化 URL + 用户名),重新添加同一站点得到同一个 id;`record_work_dispatch` 同时记下目标显示名,账户删掉后历史记录仍能显示名字。 |
| Host 校验 | `src/platforms.js` 的静态表仍是 DSL 平台的唯一来源;`bridge.js` 的任务写入与回执校验改为「静态表 ∪ 当前快照里的 CMS id」,不接受快照之外的任意字符串。 |
| 页面注入 | 任何页面都不再注入入口;只保留提取所需的临时 loading 遮罩。公众号两个 content script 删除 UI,保留提取处理器——通用提取器明确把公众号页交给它们。 |
| 进行中任务 | 保留 `syncState` 用于进度恢复;删除可回看的 `syncHistory` 与历史页。 |
| 术语 | 用户面统一「收录」(不再用「收进」)与「投递」(不再用「同步」指功能区);代码内部 `SYNC_*` 命名可保留。 |
| 文档 | `UPSTREAM.md` 记录删除清单与合并策略;README 与 manifest 描述从「同步文章」改为「收录网页、执行投递」。 |

## 不做

- 不做页面级快捷入口(悬浮按钮、公众号 iframe、编辑器入口),即使它能带来一次性便利。
- 不做独立于工作台的同步与历史;自建站只作为投递目标,不在扩展里单独发起。
- 不删适配器代码(20 个 DSL 适配器 + WordPress / Typecho / MetaWeblog 三种 CMS 协议保留),只收缩菜单展示。
- 不改投递链路与「dispatches ≠ 已发布」红线。

## 后果

- 扩展不再是可单独使用的 Wechatsync,失去「任意页直接转平台」的能力。这是有意的范围收缩。
- vendored 树与上游 diff 扩大;每次合并上游都要处理删除清单,`UPSTREAM.md` 是唯一记录点。
- 工作台新增一条只读的投递目标快照数据面(extension → helper → host),用于渲染菜单与校验目标;不涉及凭证。
- 维护面减少:历史、独立同步、页面注入三条线消失;CMS 保留并接进投递,多出一条目标快照与稳定 id 的维护线。
- CMS 账户的密码仍只存在扩展的 `chrome.storage.local`;工作台与本地助手只看到目标元数据。账户删除或重装后,稳定 id 与回执里的显示名保证历史记录还能读。
- GLOSSARY 同步:收进 → 收录,同步(功能区)退役,投递覆盖动作与记录。

## 验收场景

1. 任意 http(s) 页面不再出现悬浮按钮;清空扩展存储后也不出现。
2. 公众号文章页与后台编辑页没有任何插件 UI,但收录仍能提取正文。
3. 侧栏只有收录 / 投递 / 账号三个 tab,默认收录;设置只有齿轮。
4. 投递页只显示工作台下发的任务与进度;没有当前页同步入口,没有历史页;工作台投递时已打开的侧栏自动切到投递页,没打开则不弹窗。
5. 账号页保留平台登录态与 CMS 自建站(CMS 账户可增删、可测试连接)。
6. 工作台发布对话框列已登录的 DSL 平台;未登录/隐藏的在「更多」里;登录后重开出现。
7. 加一个 WordPress 账户后,发布对话框出现「自建站」目标;投递后草稿链接进入 `dispatches`;删掉账户后历史记录仍显示站点名。
8. 收录链路(整页/选区,含公众号页)不变:落 inbox → 灵感。
9. 投递链路不变:outbox → 适配器 → 草稿 → receipts → dispatches;status 不动。
10. `npm test` 全绿;扩展构建可加载。

## 考虑过的替代

- **双身份、入口收进侧栏**:保留独立同步/历史/CMS,只删页面注入。否掉:两套数据模型仍要解释,维护面不变,只是把症状藏进侧栏。
- **维持现状**:否掉:每个不落工作台的能力都会继续长出自己的入口与状态,FAB 只是第一个。
- **把 FAB 改成一键收录**:否掉:与「任何页面不注入入口」冲突;收录的确认、标签与冲突处理属于侧栏。
- **CMS 只在扩展里保留、不接工作台**:否掉:这正是当前的问题——工作台不知道、也记录不到;保留能力却不让它进入投递闭环,等于留一个更隐蔽的暗门。
