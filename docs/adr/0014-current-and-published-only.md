# 作品只存当前稿与发布稿:会话转录承担「上一版」,不再做快照

Status: accepted(2026-11-20 与用户逐项定案;已实现。取代 0006 的写回快照/`aiArticle`/人工改动相位,以及 0006 的版本回退)

## 背景

0006 用 `production.snapshots` 保存每次写回,用 `aiArticle` 保存 AI 最后一版,用 `pen` 徽章标「人工修改中」,让用户在校样浮层里裁决冲突、回退版本。实际使用暴露出两个问题:

- 状态管理成本远高于收益:用户改稿、会话改稿、再改稿,每一步都要落快照;UI 要解释快照、版本、字段级冲突,用户只想知道「现在这篇是什么」「发出去的到底是什么」。
- 真正能说明「用户怎么改的」的材料不在快照里,而在**创作会话的对话转录**里:用户对 AI 说「第二段太硬,改成口语」「标题不要问句」,这些调整比字段 diff 更完整。用户原话:「学习风格时默认把对应创作对话和发布稿一起给 AI 做风格迭代,完全不需要状态管理,还能读到用户在对话中让 AI 进行的调整。」

因此保存与「人工识别」一起降级:只保留当前稿、发布稿和会话指针。

## 决策

| 事项 | 决策 |
| --- | --- |
| 当前稿 | 作品编辑器直接编辑 `Work.current`;输入停顿约 700ms 自动保存,关闭编辑器前强制 flush。UI 显示「已保存 / 保存中 / 有改动未保存」,不设独立「保存」主按钮(保留 Ctrl/Cmd+S 立即保存)。 |
| 发布稿 | 用户确认发布时,把当时的 `current` 深拷贝为 `published` 并 `Object.freeze`(数据层只读);之后编辑只改 `current`。作品页/编辑器用 `published` 与 `current` 的哈希比较显示「有未发布改动」,不存 diff。 |
| 无快照 | 不存 `snapshots`、`aiArticle`、`savedHashes`、字段级历史、版本列表;不提供回退到上一版。迁移时一次性丢弃旧快照,只保留当时最新稿;已发布作品用当前稿生成第一份 `published`。 |
| 无人工改动标识 | 删除 `pen` 徽章、`by:'user'` 快照、`phaseOf` 的「人工修改中」。作品状态只显示草稿 / 已投递 / 已发布;人工改过什么不再持久化。 |
| 冲突防护 | 保存携带 `baseRev`;若 host 的 `rev` 已前进(通常是创作会话写回),不覆盖,保留编辑器里的用户文本,显示非阻塞横幅「会话写回了新版本」,给「载入新版 / 保留我的并覆盖」两个选择。选择前不接受自动保存。这是唯一保留的写回冲突机制。 |
| 会话指针 | `Work.sessionIds` 记录创建/写回这篇作品的创作会话 ID;只存 ID,不复制转录。创建作品时能从 `openWorkspace`/`connectWorkspace` 拿到 ID 就立即记;拿不到时在首次写回由 host 补。 |
| 上一版从哪来 | 需要「AI 最后一版 vs 发布稿」时,读创作会话转录,取 AI 最后一次完整成稿(通常是最接近发布的写回)作为对照;不在作品里另存。转录不可读时,风格学习只用发布稿,并在 UI 标注「未读到创作对话」。 |
| 风格学习入口 | 作品页/作品编辑器选 1..n 篇 →「学习写法」。host 按每篇 `sessionIds` 用 `sessionQuery.readSession` 读转录,过滤成用户消息 + AI 各版输出(丢工具调用与噪音),按预算截断,拼上 `published` 正文与现有风格卡/规则。 |
| 风格学习会话 | 一律新开一个风格学习会话(不在原创作会话续聊),只允许写回候选规则/风格卡;不自动启用,用户逐条接受/拒绝。原创作会话只读,不被修改。 |
| 转录不可读 | 会话已删/日志损坏/宿主不提供 `sessionQuery` 时,退化为只读 `published` 做风格学习;UI 明确提示少了对话材料,结果仍可接受/拒绝。 |
| 批量学习 | 支持多篇一起学;每篇独立汇总,风格建议去重后统一列出;来源作品可追溯。 |

## 不做

- 不做自动快照、不做定时备份、不做版本树、不做字段级 diff 存储。
- 不做「人工改动」高亮、不做 AI/人工双栏对比界面。
- 不把完整会话转录复制进 `state.json`;只存会话 ID,使用时现读。
- 不做跨设备同步;转录以本机 DSH 会话日志为准。

## 交互流程

1. 打开作品编辑器:左侧标题/封面文案/正文/封面与配图,右侧实时 Markdown 预览;输入即改 `current`,约 700ms 后顶栏显示「已保存」。
2. 创作会话同时写回同一篇:编辑器顶栏出现横幅「会话写回了新版本」;用户可载入新版或保留自己的文本覆盖;未选择前自动保存暂停。
3. 用户点发布并确认:`current` 冻结成 `published`,作品页状态变「已发布」;继续编辑正文,作品页出现「有未发布改动」,`published` 不变。
4. 用户在作品页选三篇作品点「学习写法」:新开风格学习会话,host 把三篇的对话转录与发布稿一起交给它;会话给出候选规则/风格卡,用户在风格页逐条接受。
5. 其中一篇的创作会话日志已被清掉:风格学习仍继续,但提示「这一篇只读到发布稿」;其余两篇正常使用转录。
6. 迁移旧数据:每篇旧成稿取最新 `production` 作为 `current`;若 `status:'published'` 则同内容生成 `published`;旧 `snapshots`/`aiArticle` 全部丢弃,不提供回退。

## 验收场景

1. 编辑器输入后 1 秒内落盘;刷新页面内容不丢;关闭编辑器再打开,光标内容与关闭前一致。
2. 发布后改标题:作品页仍显示「已发布」+「有未发布改动」;重新打开 `published` 仍是旧标题。
3. 发布后再次发布:新 `published` 覆盖旧文本,`publishedAt` 更新;没有旧版本入口。
4. 会话在编辑器打开时写回:出现冲突横幅;选「保留我的」后用户文本不被覆盖;选「载入新版」后编辑器换成会话文本。
5. 选两篇有会话记录的作品学习:host 读到两篇转录;候选规则带来源;接受后规则进入风格页,未接受的不生效。
6. 选一篇无会话记录的作品学习:仍能生成基于发布稿的建议,UI 标注材料缺失。
7. `state.json` 中不存在 `snapshots`、`aiArticle`、`savedHashes`;`npm test` 全绿。

## 后果

- `src/ops.js` 的 `update_production` 改为 `update_work`;`rev` 继续做乐观锁,但不再写快照。
- `client/proof.jsx` 由 `client/work-editor.jsx` 取代;内容页的 `phaseOf`/`PhaseBadge`/`IntakeBar` 删除或改成作品状态。
- 已实现 `src/style-material.js` 与 host 路由 `style/learn`:读 `sessionQuery.readSession`、过滤转录、拼发布稿,返回预填 prompt;`client/learn-from-works.jsx` 选 1–6 篇作品,`client/session-link.js` 新开风格会话。候选规则经 `writing_desk_add_rule` 进 proposed,候选风格卡经 `writing_desk_add_style` 且 `activate:false`,不自动启用。
- `sessionQuery` 不可用、会话读不到或作品没有登记会话时,退化为只读发布稿,并在 `missing` 与 prompt 中标注;这是已知降级,不阻塞主流程。

## 回滚

保留迁移前 `state.json` 备份;回退旧版本时恢复备份。新版本写出的 `works`/`published` 对旧版本不可见,不能无损降级。
