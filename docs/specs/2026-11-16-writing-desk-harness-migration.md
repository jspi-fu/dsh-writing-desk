## Problem Statement

一个图文创作者在 DeepSeek Harness（DSH）里用图文创作台工作时，遇到四件事：碎片化灵感难以收集与整理；自己的写作风格库不好维护；缺少从成稿到发布的一键流程；配图困难。

现有工作台虽然挂在 DSH 侧栏，鉴权、HTTP、模型调用、工具执行和 UI 挂载都来自宿主，但领域能力几乎全是插件自己的 JS：成稿流水线自己拼提示词、自己编排生图、自己维护状态；同一条灵感上有四套互相独立的状态字段、两条写路径、四个面板各写一套「已成稿 / 已排期」判断，于是出现「正文已经写好却显示未成稿 / 未排期」，重新成稿甚至会清空写好的正文。

与此同时，工作台想「更贴近 DSH 原生」，但 DSH 架构里没有特权核心，一切皆插件；把领域能力硬塞进会话或工具注册表，只会在另一个地方重新造一套 JS 领域系统。创作工具与 skill 如果全局注册，还会出现在用户编程、做视频等其他模式里，造成干扰。

创作者真正要的不是「原生」这个标签，而是：少重复造轮子、状态只有一个权威、工作流不断裂。

## Solution

把工作台收敛为「灵感 → 聚合 → 成稿 → 发布 → 风格迭代」的一体化闭环，并按三层落位：

1. **领域层留在插件**：灵感是最小输入单位；「胶囊」是持久化的命名灵感集合，只是更好梳理呈现灵感的 UI 设计；「成稿输入」统一解析为一组灵感 ID——单个灵感、多选灵感、单选胶囊、多选胶囊都走同一个成稿入口。新建纯 reducer 统一所有状态迁移与共享谓词，让面板不再各说各话。
2. **AI 动作层交回 harness**：在独立的「创作模式」（Agent Preset）scope 内注册 tool 与 skill，其他模式看不到；工作台 UI 仍全局可用。粗粒度 tool 负责成稿，skill 承载风格与写作规则。
3. **发布交给外部工具**：不自研平台发布。导出 Wechatsync CLI 原生格式的 `article.md + images/` 文件夹与可复制命令；上传后询问用户是否视为已发布，默认是、可手动改，不写假状态。

编辑器用自带统一组件替换散落的 textarea，不绑定第三方编辑器插件；灵感收集只借鉴 stashdock-dsh 的字段与交互设计，不产生运行时依赖；数据面板降级为可选模块。

## User Stories

1. 作为图文创作者，我希望在一个工作台里完成收灵感、聚胶囊、成稿、排期、发布和风格迭代，以便不用在多个工具之间倒来倒去。
2. 作为灵感速记者，我希望一句话、一个链接、一张图、一个视频都能记成一条灵感，以便碎片素材不再丢。
3. 作为灵感速记者，我希望速记卡只填标题、正文或链接、来源、标签、来源类型这几项，以便记录足够快。
4. 作为灵感速记者，我希望区分「我写的」和「AI 生成的」素材，以便日后筛选时知道来源。
5. 作为灵感整理者，我希望按选题、风格、素材类型给灵感打标签，把标签当成选题资料架，以便按项目取用。
6. 作为灵感整理者，我希望搜索是多词子串匹配并支持按使用频次排序，以便高频灵感自然浮上来。
7. 作为灵感整理者，我希望批量改标签先给我看 diff 预览并带版本校验，以便 Agent 的自动整理不冲掉我手动的分类。
8. 作为正在写稿的人，我希望收集灵感时不打断当前草稿，只有我点「插入」才落到光标处，以便思路不被打断。
9. 作为视觉思考者，我希望灵感像应用图标一样散落在画布上，以便自由摆放。
10. 作为视觉思考者，我希望把几个灵感图标拖到一起变成一个「胶囊」，以便把相关素材收成一堆。
11. 作为胶囊整理者，我希望给胶囊命名并保存，以便下次直接从胶囊继续写。
12. 作为胶囊整理者，我希望解散胶囊后成员灵感仍独立存在，以便整理不会因为合并而丢失原始素材。
13. 作为成稿者，我希望选中一个灵感就能成稿，以便最快开始。
14. 作为成稿者，我希望多选几个灵感一起成稿，以便把分散素材合成一篇。
15. 作为成稿者，我希望选中一个胶囊整体成稿，以便按选题批量产出。
16. 作为成稿者，我希望多选几个胶囊一起成稿，以便做系列内容。
17. 作为成稿者，我希望所有这些选择都进同一个成稿入口，以便不用记「灵感怎么发、胶囊怎么发」两套操作。
18. 作为灵感作者，我希望点开灵感进入的是编辑界面，而不是成稿浮层，以便改字段和生成是两件事。
19. 作为灵感作者，我希望在编辑界面改标题和正文并能撤销，以便放心修改。
20. 作为正文编辑者，我希望整篇正文用统一的 Markdown 编辑器编辑，带高亮、行号和查找替换，而不是一个裸 textarea，以便长文也好改。
21. 作为正文编辑者，我希望编辑器有实时预览，以便边写边看效果。
22. 作为正文编辑者，我希望编辑器的撤销与工作台的操作撤销语义保持一致，以便撤销行为可预期。
23. 作为成稿者，我希望成稿过程里标题、正文、封面首图和配图一边生成一边填进格子，以便看到进度。
24. 作为成稿者，我希望笔记和文章两种体裁都能选，以便适配小红书与公众号、知乎。
25. 作为成稿者，我希望写作时自动套用我的风格卡与写作规则，以便成品像我写的。
26. 作为成稿者，我希望「成稿产物」与灵感自身的标题正文互不覆盖，以便原始素材不被生成结果毁掉。
27. 作为状态敏感的创作者，我希望成稿完成后各页面一致显示「已成稿 / 可排期」，以便不会一处说成了、一处说没成。
28. 作为状态敏感的创作者，我希望成稿被取消或中断时已经写好的正文被保留，以便白等一场不丢稿。
29. 作为状态敏感的创作者，我希望重新成稿不再清空上一次写好的正文，以便重试不会毁稿。
30. 作为状态敏感的创作者，我希望手动改状态后系统依据成稿产物和排期自动对齐，以便不会产生「已成稿却标成灵感」的脏状态。
31. 作为排期者，我希望把稿子拖到日历某一天完成排期，以便日程一眼看清。
32. 作为排期者，我希望待排期区只列真正可排的稿子，以便灵感不会被误当成稿子排进去。
33. 作为排期者，我希望「下一条要发的」始终在右上角，以便不用翻日历。
34. 作为 DSH 多模式用户，我希望创作工具与 skill 只在「创作模式」里出现，以便编程、做视频时不被写作工具干扰。
35. 作为 DSH 多模式用户，我希望工作台侧栏在哪个模式都能打开，以便随时记一句灵感。
36. 作为 DSH 用户，我希望用现有的模式切换入口进入创作模式，而不用插件自己造一套模式 UI。
37. 作为创作模式用户，我希望在 DSH 会话里通过 tool 触发成稿，以便写作动作真正走 harness 的工具链。
38. 作为创作模式用户，我希望写作规则以 DSH Skill 形式提供并由模型按需加载，以便提示词不常驻占用上下文。
39. 作为发布者，我希望工作台导出 Wechatsync CLI 能直接吃的 `article.md + images/` 文件夹，以便不用手工整理图片路径。
40. 作为发布者，我希望工作台给出可复制的 `wechatsync sync` 命令，以便不用记参数。
41. 作为发布者，我希望先用 `--dry-run` 预览再真发，以便减少误发。
42. 作为发布者，我希望上传后系统问我「是否视为已发布」，默认是、也能改成否，以便状态由我确认而不是系统瞎猜。
43. 作为发布者，我希望之后还能手动改发布状态，以便平台侧的操作结果能被补记。
44. 作为发布者，我希望工作台绝不自动把「同步到草稿箱」写成「已发布」，以便数据不撒谎。
45. 作为风格维护者，我希望对成稿做反馈或导出稿子后，规则被提炼并写进风格卡，以便风格库越来越像我。
46. 作为风格维护者，我希望新规则在下次成稿时自动生效，以便迭代形成闭环。
47. 作为风格维护者，我希望把风格规则导出成 DSH Skill，以便其他场景复用。
48. 作为复盘者，我希望手动录入、粘贴 CSV 或导入账号数据，以便看到内容表现。
49. 作为复盘者，我希望数据面板是可选模块而不是主链路，以便不想做数据时也能顺畅通稿。
50. 作为中英文用户，我希望界面语言和生成语言跟随 DSH 设置，也能固定，以便跨语言写作顺畅。
51. 作为桌面与网页双端用户，我希望内容在本机统一存储，以便两边接着用。
52. 作为隐私敏感用户，我希望数据与密钥只在本机，以便不担心外泄。
53. 作为新手，我希望第一次打开有示例数据，清空后换成自己的，以便先看懂再上手。
54. 作为插件维护者，我希望状态迁移集中在一个纯函数模块里并有测试，以便改一处不会撞出四套口径。
55. 作为插件维护者，我希望新增工具时不会误注册到全局作用域，以便不污染其他模式。
56. 作为用户，我希望每个阶段都能独立验收和回滚，以便迁移中出问题能退回去。

## Implementation Decisions

- **模块边界**：新增纯状态 reducer 模块，统一事件与迁移；新增成稿输入解析模块，把单/多灵感与单/多胶囊归一为灵感 ID 集合；新增统一编辑器组件替换现有散落的 textarea；新增发布导出辅助模块；新增创作模式的 preset 声明、tool provider 与 skill provider；风格闭环接线到现有规则提案与 Skill 导出能力。`src/ops.js`、`src/produce.js`、`src/store.js` 的角色调整为由 reducer 统一裁决，Store 退回纯持久化。
- **领域模型**：胶囊作为持久化的一等实体，字段包含标识、名称、成员灵感 ID、创建时间；成员灵感保持独立。成稿输入是解析结果，不再区分「灵感成稿」和「胶囊成稿」两套流程。`production` 字段与 `draft / ready` 状态保留，排期规则继续依赖它们；现有 `drafts.*` 遗留口径并入统一谓词或移除重复判断。来源类型沿用 `contentOrigin` 的区分；批量改标签带 revision 乐观锁。
- **状态机接口**：reducer 定义 `start / articleWritten / done / fail / cancel / schedule / unschedule / setStatus / publish` 等事件对状态元组的原子迁移，并导出共享谓词 `isDrafted / isScheduled / panelState` 供 Host 与 Client 共用。允许手动改状态，但改后必须由 reducer 依据成稿产物与排期自愈对齐。
- **API 契约**：一个操作两个调用方——同一 Host 服务方法，UI 侧经 Remote 调用，Agent 侧经创作模式内的 tool 调用；tool 接受成稿输入 ID 集合与选项，结果写回同一 reducer。skill 以 SKILL.md 形式由 preset 内的 skill provider 与消费 tool 提供。发布导出产生 CLI 原生文件夹与命令字符串，不调用平台 API、不解析 CLI 输出。
- **作用域隔离**：tool 与 skill provider 只作为创作模式 preset 的 plugins 子项注册，不写全局 Loader 行；工作台 UI 仍在全局 slot。不使用命名空间前缀或 `when` / `restrict` 门控充当隔离（那不是真隔离）。
- **技术澄清**：DSH 没有可复用的内置编辑器，因此自带统一 Markdown 编辑器；不接入 stashdock-dsh 运行时，只借鉴其字段与交互设计；Wechatsync CLI 只是本地桥、发布在浏览器扩展里、只到草稿箱且无可靠成功信号，因此发布状态由用户确认。
- **交互约定**：拖拽聚合为胶囊；四种选择共用成稿入口；点灵感进编辑界面而非成稿浮层；上传后弹确认；状态可手动覆盖。
- **阶段顺序**：编辑界面与统一入口先行 → 状态机权威 → 创作模式与 harness 动作层 → 发布交接 → 风格闭环与面板降级。每阶段有验收标准与回滚方式。

## Testing Decisions

- **好测试的标准**：只断言外部可观察行为——给定领域状态与一串操作，断言最终状态、共享谓词的判定结果、导出产物的文件与命令；不断言 reducer 被调用几次、内部字段怎么存、UI 组件怎么渲染。
- **测试接缝**：只用一个主接缝——Host 领域模块 API，与现有 `test/host.test.js` 同一层，直接调用 ops / Store / Producer / 新 reducer / 导出辅助函数，不启 HTTP 服务、不渲染 UI。所有领域行为都在这层验证。
- **覆盖模块**：状态机四个历史不一致场景；成稿输入的四种来源解析；胶囊成员关系与解散；发布导出文件夹与命令；风格规则提案、写入、套用与 Skill 导出；既有 ops / Store / Producer 回归。
- **先例**：`test/host.test.js` 用 `node:test` 直接调用领域模块、临时目录与模拟模型；`test/client-wiring.test.js` 做静态接线检查。本 spec 沿用同一种测试形态，不引入新框架。
- **验证而非自动化测试**：Agent Preset 的 scope 可见性用现成 `cordis_inspect_query` 读 Host catalog；UI 槽位、编辑器与拖拽交互在现有 Web GUI 里人工确认。不新增测试专用入口，不做客户端 UI 自动化测试。

## Out of Scope

- 各具体流程的 skill 与 tool 的逐个接口打磨——留到后续讨论；本 spec 只固定它们隔离注册在创作模式这一决策。
- 把领域状态、胶囊、排期、复盘搬进 harness 核心或改成会话驱动。
- 接入 stashdock-dsh 运行时或依赖任何第三方编辑器插件。
- 自研平台发布、平台授权、凭据管理，或自动回写 `published` 状态。
- 把文章数据面板做成主链路核心能力。
- 客户端 UI 自动化测试、新增测试接缝、测试专用代码入口。
- 删除 `production` 字段或 `draft / ready` 状态；推翻已有本地存储与桌面/网页共用机制。
- 本 spec 阶段的任何代码改动——只产出 spec。

## Further Notes

- 领域词汇以 `GLOSSARY.md` 为准：灵感、胶囊、成稿输入、成稿产物、稿子、排期、发布、草稿、待发布。
- 架构依据见 ADR `0001-writing-desk-architecture-and-harness-migration.md`（accepted）：DSH 没有特权核心，「原生」只意味着进入 profile 默认 bundle 组合并消费 core service 注入；创作模式即 Agent Preset 的 scope 层。
- 实现前需实测两项，均不阻塞 spec：页面连接后用 `cordis_inspect_query` 复测 Client scope 的 tool/skill 可见性；确认 Wechatsync 浏览器扩展是否已连接（不阻塞导出功能）。
- 用户已确认测试接缝：一个主接缝（Host 领域模块 API）+ 两处外部验证，不新增代码 seam。
